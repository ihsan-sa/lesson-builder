## Top-5 design suggestions
1. **Make the run state executable, not narrative.** Introduce a versioned `lesson-run.json` validated at every phase boundary, holding `lesson_file`, `course_name`, deploy target, approval digest, branch/base SHA, stash OID/origin branch, media/artifact manifests, and open findings; render `lesson_build.log.md` from it instead of using Markdown as mutable state.
2. **Use a Git worktree for updates.** Create a run-id worktree from an explicitly verified base, build and commit there, then merge/cherry-pick only after approval; the user's dirty working tree never needs stashing or popping, eliminating the highest-risk recovery logic and same-branch contamination.
3. **Define chat protocols once.** Put tag grammars, payload schemas, limits, thread eligibility, and display behavior in a shared registry consumed by `buildSystemPrompt`, `processResponse`, the proxy, and generated documentation; add round-trip fixtures for every valid and invalid block.
4. **Replace regex/line-range splicing with structural transforms.** Parse JSX with Babel, assign stable component/asset IDs, mutate AST nodes, and compute asset reachability from imports/props/CSS before deletion; this removes helper misclassification, line drift, generic media recipes, and false orphans together.
5. **Add two executable acceptance scenarios with fault injection.** A six-topic new build and a dirty-tree targeted update should validate every manifest, interrupt/resume after approval, collide branch names, fail one producer/reviewer/build/push, and round-trip runtime protocols; make these fixtures the release gate for the skill payload.
